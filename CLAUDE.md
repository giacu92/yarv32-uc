## Project

RV32IMAC + Zicsr + Zifencei RISC-V core for a **Gowin GW2AR-18C** FPGA (QFN88) on a Tang Nano 20k. Clock: 25 MHz single-ended from an MS5351M generator (CLK0, PIN10, LVCMOS33) — not the stock 27 MHz oscillator. **Active build: 50 MHz via on-chip rPLL** (`clk_core = clk_i × 10/5`, IDIV_SEL=4/FBDIV_SEL=9/ODIV_SEL=16, VCO 800 MHz, period 20 ns) — re-closed at **50.017 MHz** on the 64-bit fetch-rewrite + target-span design (2026-08-27). A **branch predictor** (gshare 128×2b PHT + 7-bit GHR + 8-entry RAS, prediction-at-decode, execute-as-judge) was added 2026-08-28 and resized 2026-08-30, sim-verified (all oracles/cosims/TBs green). With linker relaxation also enabled the same day: **CoreMark 1.98 CM/MHz, Dhrystone 0.88 DMIPS/MHz**. PHT depth is set by TIMING, not accuracy — it is read combinationally at decode and that read feeds fetch's launch/inflight logic in the same cycle, so a 512-entry table cost ~1 ns of slack for 0.65% of cycles (see `rv32_pkg.sv`). **50 MHz re-closed WITH the predictor on 2026-08-31** (worst setup slack **+0.093 ns**), after three changes landing together: PHT sized down to 128, the ALU result mux reordered by arrival time, and the PnR algorithms set to timing priority. `BP_EN=0` remains the fallback but is no longer needed. Fetch then learned to **launch the redirect target in the redirect cycle itself** (2026-08-31, `e1bfba5`) — one cycle off every taken branch, predicted or not: **CoreMark 2.14 CM/MHz (466120 cyc/iter), Dhrystone 0.93 DMIPS/MHz (608 cyc/iter), quicksort 48521 cyc**. That build re-closed at +0.002 ns, which is inside the ~0.7 ns run-to-run noise and predates the `req_pc_q` clock-enable in the same commit — treat it as a tie until several seeds agree, not as a measured margin. **SHIPPING (2026-09-01, board-verified): the LSU capture stage is removed on the D-mem LOAD path, 50 MHz closed at +0.024 ns worst slack — CoreMark 2.37 CM/MHz (420560 cyc/iter), Dhrystone 1.05 DMIPS/MHz (537 cyc/iter), quicksort 44833 cyc, all on the GCC 14.3.0 -O3 default.** A **2026-09-02 compiler sweep on this build** puts the headline at **CoreMark 2.39 CM/MHz (417809 cyc/iter, 16.71 s/2000 iter, GCC 13.3.0 -O3)** — GCC 16.1.0 -O3 420897 = 2.37, -O2 builds 437616 (GCC 14.3.0) / 439457 (GCC 13.3.0) = 2.28 / 2.27 — and **Dhrystone 1.04 DMIPS/MHz (543 cyc/iter, 200 000 runs, 2.17 s, 92 081 Dhrystones/s)**. Same tree, same firmware, `LSU_LIVE_LOAD=0` for the baseline: 474767 / 600 / 49605, i.e. **−11.4% / −10.5% / −9.6% cycles at the same clock.** CoreMark CPI 1.434 = floor 1.000 + lsu-launch 0.252 + redirect 0.061 + decode-bubble 0.010 + other 0.110. It took seven PnR runs and five separate fixes, each named by the endpoint list of the run before it, plus one FPGA regression that simulation could not see; the sequence is in the run-by-run notes below, the durable rules in plan items 1b-1f. **The LSU capture stage was then removed on the D-mem path (2026-09-01)** — the D-mem bus launches combinationally from `alu_result` in `EX_IDLE` again, deleting one cycle from every load and store: **CoreMark 2.48 CM/MHz (401976 cyc/iter), Dhrystone 1.17 DMIPS/MHz (486 cyc/iter), quicksort 40154 cyc**, all oracles/cosims/TBs green. Removing it on **both** paths first failed PnR hard (**-5.533 ns, 39.164 MHz**): the peri port feeds bridge + crossbar + slave address decode, all combinational in the address phase, so the ALU was driving three levels of fabric in one cycle — every one of the 25 worst paths ran from the regfile read output into the UART's register write enables. The peri launch keeps its capture cycle, which costs nothing measurable (MMIO is outside every timed region: 8 cycles on quicksort, 4 on CoreMark, 0 on Dhrystone). **PnR on the split version has NOT been run yet.** Both reserve slack levers were implemented the same day and are live behind parameters (`MUL_SHARED_DSP`, `BP_PUSH_LOOKUP`, **both default 0** — the shipping value; their module defaults said 1 until 2026-09-02, which was harmless only because `rv32_pkg` overrides them) so PnR can move one variable per run — see items 1c and 1d. Pre-fetch-rewrite design closed at 40.281 MHz (2026-08-25). Fallback: 25 MHz bypass (also diagnostic — removes rPLL) via 3 lines in `top_module` + re-comment SDC clock + `global_freq 25.000`.

**Status:** fetch/decode/execute + LSU + Zicsr + trap/exception/interrupt implemented. **Harvard** memory — read-only I-mem for fetch, native byte-strobed D-mem for LSU, AXI4-Lite only for peripherals. **Both memories 16 KiB (`ADDR_W=14`)**: GW2AR-18C has 46 BSRAM blocks (828 Kb); each 16 KiB memory = 8 blocks, 16/46 used. Package also carries **8 MiB (64 Mbit) SDRAM** on a separate die, unused (see plan item 2). Loads/stores/Zilx/CSR retire via native D-mem (or peri bridge) with **execute→decode forwarding** (distance-1 RAW, zero bubble).

**Machine-mode traps:** precise sync traps at execute commit — instr access fault (mcause=1), illegal instr (2), ecall-M (11), ebreak (3), load/store misaligned (4/6); `mret` returns; `wfi`=halt-until-pending; `fence`/`fence.i`=nop. `mtvec` direct+vectored. Software interrupt via `msip_peri`@0x1000_3000; timer via `clint_timer`@0x1000_1000+; external = OR of peripheral IRQs (UART)→`meip_i`. Priority MEI>MSI>MTI. Trapping instr not retired.

**Timing:** pre-rewrite closed 40.281 MHz (2026-08-25) via two register stages (LSU request, CSR read). **64-bit/2-outstanding fetch + target-span rewrite re-closed 50.017 MHz (2026-08-27)** — new instruction-buffer room comparator met 20 ns; critical path stayed on `head_q → fe_instr → c_expand → regfile → forward`. **Branch predictor dropped PnR to 47.4 MHz** (2026-08-28) — prediction-adder path fix was tried then reverted (wrong on far jumps, no IPC gain in-kernel). **Re-closed 50 MHz with the predictor on 2026-08-31, +0.093 ns worst slack**, by three independent moves:
1. **PnR algorithm selection** (`impl/pnr_check.tcl`): `-place_option 2` (timing priority) + `-route_option 1` (route by timing). Both had been at 0, which optimises compile speed. These are algorithm *selectors*, not effort levels — `-route_option 2` is *faster compiling*, not better timing. This was the single largest contributor and cost no silicon.
2. **PHT 512 → 128.** The PHT is read combinationally at decode and that read feeds fetch's launch/inflight in the same cycle, so depth is a timing parameter. At 512 the read was 6.1 ns, **3.36 ns of it pure routing** across the spread-out primitives of what is (necessarily) a 1024-FF array behind a wide LUT mux. Costs 0.65% of cycles.
3. **ALU result mux reordered by measured arrival time** — see `alu.sv`.

Two further slack levers were implemented 2026-09-01 and are **not yet PnR-measured**, each behind a parameter so a run can isolate it:
4. **`MUL_SHARED_DSP=1`** (`alu.sv`, default): one signed 33×33 product with the signedness selected on the *operands*, replacing three 32×32 products selected on their *results*. The 4-way result mux was ~2 LUT levels behind the DSP — the latest signal in the ALU — and the operand-side select rides `alu_op_t`, a flopped `de_q` field that is ready long before the operands finish forwarding. Estimated 1.5-2 ns; also folds 3 multipliers into 1. Behaviour-identical, guarded by the new `sw/isa/mul_ops` oracle.
5. **`BP_PUSH_LOOKUP=1`** (default): the PHT is read when fetch *pushes* a word into the instruction buffer, and the direction bit rides in the entry, so decode reads a flop instead of a 128-deep LUT mux. Removes the array read from the decode→fetch redirect path and makes PHT depth timing-neutral. Costs a slightly stale GHR — measured at ≈0 (CoreMark +0.2% cycles, Dhrystone −0.2%, quicksort −0.05%).

**Lesson (measured twice):** run-to-run placement noise on this design is ~0.7 ns on the same path, comparable to the whole gap being closed, so a single PnR run is not evidence about an RTL change. Also: Fmax under a loose constraint understates what PnR does when pushed.

**PnR run 7 (2026-09-01, `wb_data_o` reordered by arrival + `pred_imm` off the opcode): +0.024 ns — 50 MHz CLOSED.** Both fixes landed and the design is now converged: the two groups that were 0.15 ns apart both came out just positive, group A at **+0.024** (`regfile → forward → operand → DSP → alu_result → wb_data → de_bus.rs2_data`, still the limiter) and the fetch path at **+0.066** (`head_q → u_imem AD`). Group B's `pred_dir_target → pc_q` leg is gone from the list entirely. A gained ~0.45 ns from the writeback mux reorder, B ~0.37 ns from taking the decoder cone off the predictor's adder.
**+0.024 ns is inside the ~0.7 ns run-to-run noise, so this is a pass, not a margin.** The lesson recorded above about a single PnR run not being evidence applies to a pass exactly as it does to a fail — confirm across a few seeds before treating 50 MHz as closed for good. The cheapest remaining lever on group A is the `mul_result` 4-way mux, still 6 hops / 4.66 ns behind the DSP: put plain `MUL` (the low word, the only form any benchmark emits) on its own 2:1 and fold the three `MULH*` high words behind it, so the common case sits one level behind the DSP instead of two. Worth ~0.4-0.5 ns and free in cycles.

**PnR run 6 (2026-09-01, D-mem address mux removed): -0.423 ns / 48.965 MHz.** The D-mem endpoints are gone, so the mux removal did what it was for — but worst slack did not move outside the ~0.7 ns noise (49.6 → 48.965). **The 1.92 ns was real and bought nothing, because the D-mem path was not the limiter.** At 49.6 that had been an assumption: that run's endpoint list was never read, and the two path groups this run exposes were already sitting at the same level underneath. Removing delay from a path that is not binding is worth exactly zero — the endpoint list, not the slack number, says where to cut.
Two groups now, 0.15 ns apart, and both are addressed:
- **A, -0.423**: `regfile → forward → operand → DSP → alu_result → wb_data → forward` (back into `de_bus` or the regfile write port). **Fix: `wb_data_o` reordered by arrival time**, `alu_result` on the final 2:1 with `pc_link`/`load_data`/`csr_rdata_i` folded behind it — the same restructure `alu.sv` already applies to `result_o`, and a flat `unique case (de_i.wb_src)` had `alu_result` behind two levels.
- **B, -0.307**: `buffer head → c_expand → the decoder case tree → imm → pred_dir_target adder → issue_addr → pc_q` / `u_imem AD`. 10.3 ns of that is `src_instr32 → imm` through the decoder, in front of a 32-bit carry chain and then a BSRAM address pin. **Fix: `pred_imm = (opcode == OPC_JAL) ? imm_j : imm_b`**, selected straight off `src_instr32[6:0]` instead of out of the case tree. The predictor only ever needs those two immediates and both are pure bit permutations of the instruction word, so one comparison replaces the whole decoder cone on this path. `de_d.imm` still comes from the case tree, but that ends at a flop.
Both behaviour-neutral, verified: cycle counts identical to the digit (44833 / 493314 / 1197619), retire traces identical, predictor stats identical, and `sw/isa/bp_pred` — which is what catches a wrong `pred_imm` — passes. Not yet PnR-measured.

**PnR run 5 (2026-09-01, `MUL_SHARED_DSP=1`): -2.682 ns / 44.1 MHz — REGRESSION, reverted.** The shared 33×33 product lost 2.52 ns against the three-product form. It mapped to a single MULT36X36, so the *resource* goal was met; the timing goal failed on both halves of the prediction. The operand-side sign extension was predicted free (only bit XLEN depends on the select) and is not — the operand settles at 8.366 ns and the DSP input is not reached until 10.759, against 8.564 → 10.249 without it, **+0.7 ns on the late path**. And the post-DSP mux did not shrink: **seven** `alu_result` hops (15.414 → 20.232) against six (14.009 → 18.372), **+0.46 ns** — GowinSynthesis folds the 66-bit product's two candidate slices into the same mux tree as every other ALU candidate, so one level in RTL is not one level in fabric. `MUL_SHARED_DSP` stays 0. **Generalisable: on this device the DSP count and the DSP's contribution to the critical path are close to independent — folding multipliers together buys area, not slack.**
That run's path ended at **`u_dmem/mem_*/ADA[*]`**, the D-mem address pins, and exposed a free 1.92 ns: the address was `dmem_load_drive ? alu_result : mem_addr_q` on top of a `'0` default, two LUT levels (20.232 → 22.150) in front of a BSRAM address pin that already pays a long physical tail. **The mux was redundant** — `mem_addr_q` is loaded from `alu_result` and `de_i` is held while a request is outstanding, which the `ifdef VERILATOR` assertion has been checking all along — so the D-mem address is now an unconditional wire from `alu_result`, and every payload field on both ports dropped its `'0` gating with it. Zero cycle cost (cycle counts and traces unchanged). Not yet PnR-measured.

**PnR run 4 (2026-09-01, stores re-captured + `EXEC_REDIR_INCYCLE=0`, `MUL_SHARED_DSP=0` / `BP_PUSH_LOOKUP=0`, target 45 MHz): -0.161 ns / 49.6 MHz — TARGET MET**, 4.6 MHz of margin over the 45 MHz acceptance. The chain that got there, from the 39.164 MHz of run 1: peri launch re-captured (run 1 → 2, +2.8 MHz), `EXEC_REDIR_INCYCLE=0` (run 2 → 3 exposed the next path), stores re-captured (run 3 → 4, +9.5 MHz). The remaining -0.161 ns is the `regfile → operand → DSP → alu_result → ~6 mux levels → wb_data → forward` group, which had been sitting at -0.036…-0.089 ns in run 2 — i.e. exactly what `MUL_SHARED_DSP=1` targets, and it is the next run. 0.161 ns is also well inside the ~0.7 ns run-to-run noise, so 50 MHz may simply be a reseed away.
**If the design ships at 45 MHz instead of 50, `rv32_pkg::UART_CLK_HZ` must go to 45_000_000 with the rPLL.** Left at 50e6 against a 45 MHz clock, `BAUDDIV` stays 433 and the line runs at 103 687 baud against a nominal 115 200 — −10%, far outside 8N1 tolerance, and the board goes silent exactly as it did on the 10 MBaud mistake. At 45e6 the divisor is 389 and the error is +0.16%.

**PnR run 3 (2026-09-01, `EXEC_REDIR_INCYCLE=0`, target 45 MHz): -4.956 ns / 40.1 MHz.** Run 2's I-mem-address endpoints are gone, so that fix worked — but it uncovered a longer path underneath, and this time the full trace was read:
```
regfile DO[13] 2.271 -> de_bus.rs1_data 5.708 -> operand_a 8.564
  -> DSP 9.328..14.009 -> alu_result[0] 18.372
  -> dec_stall 22.012 -> buf_pop_cnt 23.617 -> fetch head_q 27.192
```
All 25 worst paths are leaves of it: `fetch head_q/count_q` (gated by `buf_pop_cnt` ← `stall_i`) and `decode hold_pc_q/hold_word_q` clock enables (also gated by `stall_i`). 8.8 ns of the path sits *after* `alu_result`.
**Cause, and it was never the address path.** Removing the D-mem capture made a store's retire depend on the effective address — `mem_misaligned` (`alu_result[1:0]`), `is_peri_live` (`alu_result[PERI_ADDR_BIT]`), the slave's accept — and a posted store retires *on its launch*, so `stall_o` has to answer "did this store launch" in the same cycle. That put the deepest combinational value in the machine on the pipeline's **control** network. The D-mem's own address pins have not appeared in any of the three reports.
**Fix: capture STORES, keep the LOAD launch live** (`EX_MEM_LAUNCH` handles peri-either-direction plus D-mem stores; only an aligned D-mem load drives live). A load never retires on its launch — it goes to `EX_MEM_WAIT` and retires on `rvalid` — so `mem_req_pending`, which is flop-only, already holds decode and nothing about the load's launch needs to reach `stall_o`. Keeps 78% of the win (CoreMark: 62778 loads vs 17815 stores). Cost: quicksort 41325 → 44833, CoreMark 408803 → 423062 cyc/iter (2.44 → **2.36 CM/MHz**), Dhrystone 487 → 537 (1.16 → **1.05 DMIPS/MHz**, store-dense via `strcpy`). Against the original both-captured baseline that is still −7.4% / −10.1% / −10.4% cycles. Not yet PnR-measured.

**PnR run 2 (2026-09-01, peri-split, `MUL_SHARED_DSP=0`, target 45 MHz): -3.812 ns / 42.0 MHz.** The peri paths are gone — the split worked. The new worst eight paths all end at **`u_imem/mem_mem_0_*/AD[*]`**, the instruction memory's ADDRESS pins, from `u_cpu/u_regfile/regs_regs_0_0_s0/DO[17]`:
```
regfile DO -> forward -> operand -> JALR adder (rs1+imm) -> branch_target mux
           -> branch_addr_o -> fetch issue_addr -> u_imem AD[*]
```
Nothing else in the design can end at an I-mem address pin — `issue_addr` is the only path there, and `pc_q`/`pc_next_block` are flops — so the identification is by elimination, not inference. The remaining endpoints in the list (`fetch pc_q/CE`, `count_q/D`, `head_q/D`, `decode hold_pc_q/CE`) are the same signal's other fanout: `branch_valid_o` zeroes `head`/`count` and flushes the hold buffer. Roughly 9.8 ns of the 23.777 is tail *after* the branch target resolves — the BSRAM address columns are physically far, the same effect that made an issue-side range check cost -2.292 ns (see `fetch_stage.sv`).
**Fix: `EXEC_REDIR_INCYCLE=0`** (new default) — drop `branch_addr_i` from the issue mux, so only the DECODE prediction launches in-cycle. Its target is `src_pc+imm` or the RAS top, both PC/flop-derived, so it never drags the register file onto the address pins. Costs 1 cycle per execute redirect (mispredict/trap/mret): quicksort 40135 → 41301, CoreMark 402827 → 409827 cyc/iter (2.48 → **2.44 CM/MHz**), Dhrystone 485 → 485 (99.3% accuracy, almost no execute redirects). Not yet PnR-measured.
The second path group in that run, at **-0.036 to -0.089 ns**, is `regfile -> operand -> DSP/adder -> alu_result (14.3 ns) -> ~6 mux levels -> wb_data -> forward`. That is what `MUL_SHARED_DSP=1` targets, and it becomes the limiter once the I-mem leg is gone.

**PnR run 1 (2026-09-01, LSU capture removed on BOTH paths): FAILED at -5.533 ns / 39.164 MHz.** All 25 worst paths ran `u_cpu/u_regfile/regs_regs_0_0_s/DO[11]` → UART register write enables (`div_pending_q`, `tx_fifo` WRE, `tx_ie`/`rx_ie`/`tx_wptr` CE) or the CSR file; **no D-mem endpoint**. Cause: the peri port is not a slave but `axi4_lite_master_bridge` → `axi4_lite_xbar_3` → slave address decode, all combinational in the address phase, so the ALU drove three levels of fabric in one cycle. Fixed by keeping the capture cycle on the peri path only (`EX_PERI_LAUNCH`) — costs 8/4/0 cycles on quicksort/CoreMark/Dhrystone. **That split has not been through PnR yet.** Reserve levers if it still misses: collapse the `mul_result` 4-way mux (~1.5-2 ns), move the PHT lookup to buffer-push time.

**Limiter before that run: `regfile → forward mux → branch compare/target → PC redirect`.**

That limiter was the path the notes predicted would surface next, reported by the PnR run on the redirect-launch design (2026-08-31). It displaced **MUL**, which stays the one behind it: `regfile → forward → operand → DSP (3.78 ns) → alu_result ×6 → wb_data → forward`, whose `mul_result` selection (4-way among the three DSP products) still sits ~6 mux levels deep and is worth ~1.5-2 ns if more headroom is ever wanted. Stall histogram (2026-08-27) agrees from the cycle side: redirect was the largest single no-retire cost (~3.1 cyc/taken redirect, 38–50%) — exactly what the predictor targets (redirect CPI 0.374→0.102 on CoreMark). Legacy `VON_NEUMANN` build dropped.

CPU exposes 3 ports: native `imem` (RO), native `dmem` (byte-strobed), AXI4-Lite master `axi_peri`. Native→AXI conversion inside the CPU (`axi4_lite_master_bridge`); board top is pure wiring. LSU decodes `addr[PERI_ADDR_BIT]` (0→D-mem, 1→peri). Only non-bus CPU output: `dbg_stall_o`→LED0.

**The per-path timing detail is an option, and it defaults to OFF.** Without it a run still writes `impl/pnr/*.tr.html`, but that carries only the summary — worst slack, Fmax, the constraint table. The cell-by-cell dump this project's whole timing method depends on (for each failing endpoint: the slack, then one line per cell with its incremental and cumulative arrival time) goes to the PLAIN TEXT report instead, `impl/pnr/*.tr.txt` plus `*.timing_paths`. It reports the 25 worst paths per constraint group, which is the "all 25 worst paths" the run notes below keep quoting, and it is the only report that breaks a path into cells — i.e. the only way to say a thing like "8.8 ns of the path sits *after* `alu_result`". Enabled 2026-09-02 in two places so neither file surviving alone loses it: `set_option -gen_text_timing_rpt 1` in `impl/pnr_check.tcl`, and `"Generate_Plain_Text_Timing_Report": true` in `impl/rv32imac_Zicsr_Zifencei_process_config.json` (which is what a GUI run reads). **The SDC has nothing to do with it** — a missing SDC produces no failing paths at all, because PnR then falls back to unconstrained 100 MHz.

Same file, same day: `"Global_Freq"` was **55.000** while the SDC and `pnr_check.tcl` both said 50 MHz. A run through the Tcl wrapper was unaffected (`set_option -global_freq 50.000` overrides), but a GUI run — or any run not using the wrapper — constrained the design to 55 MHz and reported timing for something that is not what ships. ## Simulation (Verilator)

Builds fetch+decode+execute+native I/D-mem+peri bridge, `--public-flat-rw`.

- `sim/sim_top.sv` — wrapper preloading native I/D-mem via `$readmemh` (`+IINIT=`/`+DINIT=`). 64-bit RO `OUTSTANDING=2` I-mem, 32-bit RW `OUTSTANDING=1` D-mem. `uart_rxd_i` double-flopped for board parity; every TX-FIFO byte logs to `sim/sim_uart_tx.txt`. `UART_CLK_HZ`/`UART_BAUD` default fast (5 clk/bit); pass `-GUART_CLK_HZ=25000000 -GUART_BAUD=115200` for board-real 217.

## Architecture

Built bottom-up. Every RTL file: `import rv32_pkg::*;` + `` `resetall `` / `` `default_nettype none `` / `` `timescale 1ns/1ps ``.

### Naming
Ports `_i`/`_o`. Flops `_q`, next-state comb `_d`. Instances `u_*`. Stage debug taps `fe_`/`de_`/`ex_`, internal only (`dbg_stall_o` is the sole exported one).

### Files
- **`rv32_pkg.sv`** — **structural A/B knobs live here** (2026-09-01), one place so the board top and the sim cannot diverge: `BP_EN`, `MUL_SHARED_DSP`, `BP_PUSH_LOOKUP`, `EXEC_REDIR_INCYCLE`, `LSU_LIVE_LOAD`. **As of 2026-09-02 every module's own parameter default matches the value here** — `MUL_SHARED_DSP` and `BP_PUSH_LOOKUP` had module defaults of 1 against a package value of 0, i.e. a standalone instantiation, or a new one that forgot to thread the knob, silently picked up the measured-worse MUL form and a PHT placement that has never been through PnR. The package overriding them on every real instance is what kept that harmless, which is exactly why it went unnoticed. `top_module` passes them to `u_cpu`; `sim_top`'s parameters *default* to them and stay `-G`-overridable, so `make VPARAMS="-GMUL_SHARED_DSP=1"` still works for a sim-only A/B while `make run` measures the core the bitstream will contain. Also `UART_CLK_HZ` (= core clock, must track the rPLL — the derivation is documented at the rPLL instance in `top_module`, which no longer keeps a second copy) and `UART_BAUD` = **115200, the BOARD baud**. `sim_top` deliberately does NOT take `UART_BAUD` from here: it defaults to 10 MBaud (5 clocks/bit) to keep runs short. Copying that sim default into the package makes `BAUDDIV` reset to 4 instead of 433 and the board goes silent — done once on 2026-09-01, caught on the board, not in sim (the sim overrides it). `XLEN=32`; `cpu_mem_req_t`/`cpu_mem_rsp_t`/`cpu_mem32_req_t`/`cpu_mem32_rsp_t`/`ifetch_req_t`/`ifetch_rsp_t`. **The `CPU_`/`cpu_` prefixes are load-bearing, not decoration**: `yarv32_cache_pkg` (the cache submodule) declares the same native protocol with the same `` `YARV_MEM_* `` macros and owns the unprefixed spellings (`MEM_WIDTH`, `STRB_WIDTH`, `mem_req_t`, `mem_rsp_t`, `CACHE_WIDTH`, `cache_req_t`), so on the cache build both packages are wildcard-imported over one elaboration. Two of the shared names disagreed on their VALUE, not just their spelling — `STRB_WIDTH` is `XLEN/8`=4 here and `MEM_WIDTH/8`=8 there — and sv2v refuses such a tree outright (`identifier "mem_req_t" ambiguously refers to the definitions in any of rv32_pkg, yarv32_cache_pkg`), which is what had taken `lint-yosys` and `gatesim` offline. Renamed CPU-side 2026-09-04 so the two name sets are disjoint; the cache package was left untouched, being the canonical owner. The cache-line-wide pair (`CACHE_WIDTH`/`cache_req_t`/`cache_rsp_t`) was deleted here rather than renamed — no CPU RTL ever read it, and a cache's geometry belongs to the cache package. The `` `YARV_MEM_* `` macro block itself IS duplicated verbatim in both packages behind a shared `` `ifndef YARV_MEM_TYPES_SV `` guard, deliberately: the copy is what lets the CPU build with no cache submodule checked out. Keep the two texts identical — the guard means a divergence is silently resolved in favour of whichever package compiled first, not reported. `PERI_ADDR_BIT`=28; peri windows `UART_BASE`=0x1000_0000/4K, `MTIMER_BASE`=0x1000_1000/8K, `MSIP_PERI_ADDR`=0x1000_3000/4K. Decode types: opcodes (incl `OPC_AMO`), `alu_op_t` (incl `ALU_LX`), `wb_src_t` (incl `WB_CSR`), `csr_op_t`/`csr_addr_t`, `sys_op_t`, `MCAUSE_*`, `MSTATUS_*`, `MTVEC_DIRECT/VECTORED`. Packed `de_t` D/E struct. **`alu_src_a_t` / `alu_src_b_t` were narrowed 2026-09-02, and their WIDTH is a timing parameter**: both muxes sit on `regfile → forward → operand → DSP → alu_result → wb_data`, the design's worst path. `alu_src_b_t` held five values in 3 bits, which makes operand-B an 8:1 tree (three LUT levels) in front of the DSP; two of the five were never produced by any opcode. `ALU_B_ZERO` was dead from the start (decode's default is `ALU_B_IMM`), and `ALU_B_PC4` existed only for JAL — whose `alu_result` is *discarded* (`wb_src=WB_PC4` takes `pc_link` directly and the redirect target comes from execute's own `branch_target` adder), so JAL now selects `ALU_B_IMM`. That drops the enum to 2 bits, the mux to a 4:1 (two levels), takes a bit out of `de_t`, and — the point — removes `pc_link`, an adder output, from the operand mux entirely. `ALU_A_CSR` went the same way: never produced, and it hung `csr_rdata_i` on the operand-A mux. **Every operand input is now a plain flop field of `de_i`** — nothing that has to be computed in the same cycle reaches an operand. **Branch-predictor types**: `pred_source_t` enum `{PRED_NONE,PRED_DIRECT,PRED_PHT,PRED_RAS}`; `bp_lookup_req_t`/`bp_lookup_rsp_t`/`bp_train_t`; **BP geometry localparams** `BP_PHT_DEPTH`=128/`BP_PHT_IDX_W`=7/`BP_GHR_W`=7/`BP_RAS_DEPTH`=8 (single source of truth — the index-carrying struct fields are all `BP_PHT_IDX_W` wide); `de_t` carries `pred_valid`/`pred_taken`/`pred_target[32]`/`pred_source[2]`/`pred_pht_index[7]` (~43 bits) riding D/E to execute for compare against resolved outcome.
- **`fetch_stage.sv`** — carries the push-time prediction per buffer entry when `BP_PUSH_LOOKUP=1`: `buf_pred_lo_q`/`buf_pred_hi_q`/`buf_ghr_q`, 9 bits × 8 entries = 72 flops, written from `bp_push_i` alongside the word. Both lookup PCs (`push0_pc`/`push1_pc`) are combinational off flops (`req_pc_q`, `pc_q`), so the PHT read they drive is flop-to-flop with a whole cycle. Head and head+1 export the prediction fields (head+1's high-half bit is needed because the same-cycle target stitch re-stashes head+1's upper half). 64-bit, 2-outstanding, depth-8 (32-bit-word) instruction buffer. One 64-bit access delivers two 32-bit words, split into PC-stamped buffer entries (0/1/2 pushes/cyc); decode still consumes the head exactly as the old F/D word — decode itself unmodified. `pc_q` advances by 8; `req_pc_q` holds the real in-flight PC. **Split PC stamp**: the half containing the fetch PC is always stamped `req_pc_q` so decode's `fe_pc[1]` picks the right halfword — stamping the high half with a computed address instead clears bit[1] and misrouted a `jalr` (fixed 2026-08-26, latent because the in-place oracle never redirected into the high half). `inflight_q[1:0]` caps outstanding at 2 (backed by the I-mem's depth-2 response skid); a redirect sets `pc_q`, kills the buffer, and arms `stale_q` (0..2 counter) so the killed path's responses are accepted and dropped by counting rather than by blocking the issue path. **Measured, `inflight_q` never leaves {0,1}**: the 1-cycle BSRAM always answers on the cycle a launch could overwrite `req_pc_q`, so the single in-flight-PC register is safe and the second outstanding slot is headroom. A `ifdef VERILATOR` assertion in the file fails the run if that ever stops holding — it is the guard for plan item 2, where a variable-latency I-mem would make the older response split at the younger read's PC stamp, silently corrupting `fe_pc`. Overflow-safe room gating: `available = 8 - count - 2*inflight`, issue needs `available>=2 & inflight<2`, fault push needs `available>=1` (a second assertion checks `count + 2*inflight <= 8`, since `available` is unsigned and would wrap). Inputs: `stall_i` (decode), `branch_valid_i`+`branch_addr_i` (execute redirect incl trap/mret/interrupt), **`pred_valid_i`+`pred_addr_i`** (decode's predicted-taken redirect, priority-merged *below* execute redirect via `pred_redirect = pred_valid_i & ~branch_valid_i`, same kill path, fires one cycle earlier). **Redirect launches in-cycle** (2026-08-31): `issue_addr = redirect ? redirect_addr : redir_launched_q ? pc_next_block : pc_q` feeds `imem_req_o.addr`, and `bus_issue` drops its range term on a redirect cycle, so the first read at the target goes out one cycle earlier than the flopped `pc_q` would allow. `redir_launched_q` defers the 8-byte advance a cycle so every adder still runs on `pc_q` — nothing but the address mux sits on the predictor's combinational path. The check sits on the response side because an `issue_addr` version of it hangs an 18-input OR-reduce off the predictor's target adder (measured −2.292 ns). Parameter must match the instantiated `native_ram`.

Costs no logic: the net already existed and the mux stays for every other consumer. It exists because the result mux is shaped for the MUL DSP (the latest signal in the block), which puts the adder two levels deep — and the whole LSU used to read the address through it. For a load, store or Zilx indexed load `alu_op` is always `ALU_ADD` or `ALU_LX`, so `sel_adder=1` and `is_mul_op=0` and the tap is bit-identical to `result_o`; `execute_stage` asserts that equality on every cycle a memory request is pending. The low bits are the real prize: the store strobes and the store lane shift depend only on `EA[1:0]`, which now come off the bottom of the carry chain instead of the top of a mux tree.
  **The 32-bit partial remainder is sound for a subtle reason — do not touch it casually.** `rem_part` is 32 bits, so bit 32 of `2*rem + next_dividend_bit` is dropped by the shift. The restoring invariant only gives `rem < divisor`, and a divisor above 2^31 admits `rem >= 2^31`, which would overflow. What actually bounds it is the DIVIDEND: after k iterations the partial remainder is also below 2^k, so entering any of the 32 iterations it is below 2^31. Instrumented over 200 006 operand pairs with divisor > 2^31, the partial remainder peaks at exactly 0x7FFFFFFF and bit 32 is never needed. **The bound comes from the 32-bit dividend and the 32-iteration count together** — widen the dividend, change the iteration count, or reuse the divider at another width, and `rem_part` must grow to XLEN+1 bits first. `sw/isa/div_ops` covers the divisor > 2^31 shapes.

A store issues and retires in the same cycle (posted, on launch accept); a load costs its issue cycle then waits in `EX_MEM_WAIT` for `rvalid`. Both orderings are architecturally legal. CSR: `csr_new` = RW:src / RS:`old|src` / RC:`old&~src`. Load alignment shifts by **`mem_addr_q[1:0]`** (registered in the launch cycle) — **never `alu_result[1:0]`** (a cycle stale — the 2026-08-25 silicon bug: a distance-1-forwarded load address selected byte 0, invisible in sim). **Traps**: `freeze=stall_i|wfi_stall`; sync traps fire in `EX_IDLE` (never launch on misaligned); `mret` retires+redirects to mepc; `take_interrupt` suppresses next instr at retire boundary or WFI wake; WFI retires once then halts until `int_pending`. Training (`bp_train_o`) fires at resolve for every control-flow instr: PHT update indexed by the **GHR snapshot** `de_i.pred_pht_index` (uses the history the branch was predicted with), GHR shift, RAS push/pop. In-order single-issue → squashed wrong-path instrs never train.

### Pipeline behaviour
**Fetch**: 64-bit/2-outstanding/depth-8 buffer. One access delivers two words; 2-outstanding keeps the BSRAM issuing through decode stalls, removing the pre-rewrite dominant bottleneck (~2.2 cyc/instr). Steady state ~1.8 cyc/instr. Harvard so fetch owns the I-mem port uncontended. Redirect kills the buffer, issues at the target in the same cycle, and counts off the ≤2 in-flight reads of the killed path (`stale_q`) instead of blocking on them. Decode also reads `head+1` (`fe_next_instr_o`/`fe_next_valid_o`=count≥2) for the same-cycle target-span stitch, driving `fe_pop2_o`.
**Decode** priority: spanning stitch > compressed hold > odd-half target > fresh low half. **Branch-target span (offset 2/6) is zero-bubble** (`target_span_complete`); **sequential span remains 1 bubble** (`span_wait`, fall-through case — removing it is dual-issue, deferred). Deferred-to-execute traps: unknown opcode, AMO funct5 11110/sfence.vma (no VM). Retiring in execute: ecall/ebreak/mret/wfi/fence/fence.i. Zicsr fully decoded+retired.
**Branch prediction**: decode predicts every classified control-flow instr — JAL/c.j/c.jal get a direct target (no BTB, zero cold-start mispredicts), conditional direction from PHT, JALR-returns from RAS; other JALR unpredicted. Predicted-taken redirects fetch one cycle early; execute stays golden resolver. Net effect on no-retire budget: redirect CPI drops ~3×, but a kill+refill bubble appears on every *correct* predicted-taken branch, charged to `imem-starve`/`other` rather than to `redirect` (no mispredict fires to attribute it). That cost was ~0.21 CPI when the predictor landed; the redirect-launch change (2026-08-31) removed one of its three cycles, leaving ~0.12 CPI in `other` and `imem-starve` below 0.001 on CoreMark. Accuracy 74/84/79% (qs/cm/dh), RAS hit 98–100%. Architectural retire stream identical BP on/off (verified: quicksort 29675 retires both ways).

### Hazard resolution (execute→decode forwarding)
`fwd_rs1`/`fwd_rs2` fire when execute retires a writeback to a register the decoding instr reads (x0 excluded): inject `ex_wb_data_i` instead of the stale async regfile read — zero bubble. Covers ALU-RAW, div-done-then-use, branch-on-dependent, load-use (load's `EX_MEM_WAIT` holds consumer via `stall_i`; `wb_en` pulse on `rvalid` drives forward). Distance-2+: harmless, async regfile read already sees the committed value. Legacy `raw_haz` bubble interlock disabled.

**Rule the forward path imposes**: a combinational value derived from D/E operands (anything downstream of `alu_result`) may be consumed **only in the cycle it's produced** — later-cycle needs must latch it. Operands can come from the bypass, so such a value sits at the end of the critical path: simulation settles it regardless of depth, silicon does not. This is how the load byte-select bug got in — first thing to check when HW/sim disagree. Audited: `store_wstrb`/`store_wdata`/`mem_req.addr`, `sync_tval`, trap bundle payload.

**Known limitations:**
- Forward path distance-1 only (correct — execute retires ≤1 writeback/cyc in order).
- M-mode only (no S/U, medeleg/mideleg, PMP). Instruction access fault implemented; instruction-address-misaligned deliberately absent (IALIGN=16 with C ext means no odd PC can arise). Cross-word sub-word accesses unhandled. MEIP is single ORed level (only UART, no PLIC — ISR must poll). Unimplemented CSR addrs silently read 0/ignore writes.
- WFI halts forever if no enabled interrupt ever arrives (legal). `fence.i`/`fence` are nops (Harvard has no D→I write path).
- Harvard: I-mem holds `.text`/`.text.init` only; rest lives in D-mem. Three learned linker/startup rules: every `link.ld` must collect small-data sections (`.srodata*`/`.sdata*`/`.sbss*`) into `.rodata`/`.data`/`.bss` (gcc's `-msmall-data-limit` default puts objects there; `objcopy -j .rodata -j .data` misses uncollected sections); `start.S` zeroes `.bss` and `a0`/`a1` before `call main`; `sp=0x4000` (top of 16 KiB D-mem — above it aliases silently, only `ADDR_W` bits decoded). `.data`@0x2000 keeps Spike co-sim disjoint; requires `medlow`.

### Open work

- **Divider bug, found and fixed 2026-09-02: `REM rd, rs1, 0` with `rs1` negative returned `abs(rs1)`.** The divider stores `abs(dividend)` and re-applies the sign to the result; the divide-by-zero path returned the magnitude with no sign applied. RISC-V requires `REM x, 0 == x`, sign included, so `rem -5, 0` answered `+5`. `DIV`/`DIVU`/`REMU` were correct. Fixed by restructuring the result as **magnitude first, sign second** — one negate applied to whichever magnitude was selected, so the normal and by-zero paths share the sign by construction instead of by duplication. `DIV` by zero must NOT re-apply the sign (the answer is -1 whatever the dividend), so that guard moved into the sign flop (`divisor != 0` on the DIV term) rather than being bypassed downstream. Side effects, all in the right direction: one 32-bit negate instead of two, one sign flop instead of two, and the 32-bit `div_divisor_q == 0` reduce (~3 LUT levels) out of the result path and into a launch-time flop `div_bz_q`. Depth unchanged — the negate moved from in front of the mux to behind it.
  **How it was found, and why it had survived.** A bit-exact model of the datapath was run against an independently written RISC-V reference over 173 889 operand pairs per form: `div` 0 mismatches, `divu` 0, `remu` 0, **`rem` 216 — every one of them with `b==0` and `a[31]==1`.** Spike confirms the expected value at the same pc. Nothing in the tree had ever tested the divider: `mul_ops` covers the multiply half, and quicksort / CoreMark / Dhrystone between them emit only ordinary positive divisions — never a division by zero, never a signed overflow, never an unsigned divisor above 2^31. **The new `sw/isa/div_ops` oracle fails with `0xBAD` on the unmodified RTL and passes with `0x600D` after the fix**, so it is not vacuous. Same lesson as `mul_ops`: the corners of the M extension are unreachable from compiled benchmark code, so they need a hand-written oracle or they are simply untested.
- **FPGA regression of 2026-09-01, RESOLVED — and the most expensive lesson in the file.** The 50 MHz-closing build reboot-looped on the board: CoreMark printed its banner and `running...`, then restarted and reprinted it. Simulation was clean throughout — every oracle, both cosims, and CoreMark to **ITERATIONS=2000** (843 509 125 cycles, `crcfinal=0x4983`, `Correct operation validated.`).
  **Root cause: a partially-driven bus.** An intermediate version dropped the zero defaults on `mem_req_o` / `peri_req_o` and drove the payload fields unconditionally, to save 1.92 ns of mux in front of the D-mem address pins. Two consequences, both invisible in simulation:
  1. **A mixed-lifetime bundle.** On a live load launch, `addr` was this cycle's `alu_result` while `wdata`/`wstrb` were the *previous* captured op's flops. Justified at the time with "the slave ignores those fields when `we=0`" — true of `native_ram` and of the AXI bridge, and exactly the reasoning that does not hold up.
  2. **Buses that never stopped switching.** 32-bit address and data into a BSRAM and into the AXI fabric toggled on every cycle of the program instead of only during an access.
  Fixed by restoring `origin/main`'s structure: full zero defaults, exactly one driving branch, and a live load launch that drives only `addr` + `wvalid` and leaves the write payload at zero. **Rule: a bus is either fully registered or fully driven from one cycle's values, and an idle bus is zero — "the receiver ignores that field" is a property of today's receiver, not of the bus.** The project had hit and fixed the same class before.
  **How it was found, which matters more than the fix.** Four hypotheses were wrong before the bisection was run: the I-mem image size, the misaligned check on live `alu_result`, `EXEC_REDIR_INCYCLE`, and the LSU capture shape. Each cost a board run. What settled it in one step was **flashing `origin/main` unpatched** (worked) and then **`LSU_LIVE_LOAD=0` + `EXEC_REDIR_INCYCLE=1`**, the known-good RTL shape, which *also* looped — exonerating the LSU and fetch changes and leaving only what was common to both patched builds. **Bisect against a known-good build before theorising; a silicon-only failure has a small, enumerable set of causes (synthesis inference, timing, bitstream) and simulation cannot narrow it.**
  Two diagnostics kept from the hunt: the trap reporter in `sw/coremark/core_portme.c` (prints mcause/mepc/mtval and parks, `#if !COSIM` — with `mtvec` at its reset value of 0 any trap re-enters `_start` and reprints the banner, which is why a reboot loop was the symptom of *nothing* rather than of a trap), and the `sw/isa/mul_ops` oracle.

1b. **LSU capture stage removed on the D-mem path — DONE 2026-09-01, closed and board-verified.** `EX_MEM_LAUNCH` is gone; `EX_PERI_LAUNCH` (peri only) and `EX_MEM_TRAP` (misaligned only) take its place. A D-mem load costs 1 no-retire cycle instead of 2 and a D-mem store 0 instead of 1; a peri access keeps its capture cycle. Same firmware images both sides: quicksort 48434 → 40154 cyc (identical 29336 retires), CoreMark 470452 → 401976 cyc/iter, Dhrystone 599 → 486 cyc/iter; CPI 1.651 → 1.369 / 1.586 → 1.371 / 1.734 → 1.429.    **Why it is a split and not a clean removal — PnR said so.** Removing the capture from both paths at once returned **-5.533 ns worst slack, 39.164 MHz**. All 25 worst paths shared the startpoint `u_cpu/u_regfile/regs_regs_0_0_s/DO[11]` and ended in the UART (`div_pending_q`, `tx_fifo` WRE, `tx_ie`/`rx_ie`/`tx_wptr` CE) or the CSR file; **no endpoint was in the D-mem**. "The memory port" is two different things: the D-mem is a slave that registers its inputs, while the peri port feeds `axi4_lite_master_bridge` (which in `S_IDLE` drives `axi.awaddr`/`wdata`/`wstrb` straight through from `req_i`), then `axi4_lite_xbar_3`, then the slave's own address decode — three levels of fabric plus a register decode, combinational in the address phase. The CSR endpoints were the same root cause one step out: `result_ready` fed off a `wready` selected by a live `alu_result` bit, so the bridge's `wready` reached `csr_we`/`wb_en`/`op_commits`. **Lesson worth keeping: before deleting a launch flop, ask what is combinational on the far side of the port, not just how deep the path to the port is.**

   PnR run 2 measured the split at **-3.812 ns / 42.0 MHz** and moved the limiter to the redirect path's I-mem-address leg, not to anything the capture removal touched — the D-mem's own address pins never appear in the report, so the live D-mem launch is affordable. That leg is addressed by `EXEC_REDIR_INCYCLE=0` (item 1e). PnR on that is the open item. If it still does not close, the reserve levers are (i) collapse the `mul_result` 4-way mux (~1.5-2 ns) and (ii) move the PHT lookup to buffer-push time. Behaviour deltas to know about, both legal and both documented in the file: a pending interrupt no longer preempts a mem op (it is taken after the access retires), and a misaligned access traps from `EX_MEM_TRAP` rather than being preempted by a pending interrupt.

1c. **`mul_result` mux collapsed — TRIED AND REVERTED 2026-09-01 (`MUL_SHARED_DSP=0` ships).** `alu.sv` parameter `MUL_SHARED_DSP` (**default 0** as of 2026-09-02; it had been left at 1, i.e. at the measured-worse form, in `alu.sv`, `execute_stage.sv` and the CPU top). One signed 33×33 product replaces three 32×32 products; signedness moves from a 4-way mux on the *results* to a 1-bit sign-extension select on the *operands*, driven by `alu_op_t` (a flopped `de_q` field, early). Behind the DSP only the low/high word select remains. Verified behaviour-identical: new oracle `sw/isa/mul_ops` passes at `MUL_SHARED_DSP=1` and `=0` in the same cycle count (131), and a deliberate mutant (MULHSU sign-extending rs2) is caught at cycle 36 with `0xBAD`, so the oracle is not vacuous. **Nothing in the tree emitted MULH/MULHSU/MULHU before this** — gcc only reaches for them on 64-bit arithmetic, which no benchmark does — so the entire signed/unsigned half of the M extension was unguarded; that is why the oracle came first. Unknown until synthesis: whether a 33-bit operand tiles as well onto MULT18X18 as a 32-bit one (it pads to 36) — **check the resource table, not just the slack**.

1e. **Execute redirect no longer launches in-cycle — DONE 2026-09-01, closed and board-verified.** `fetch_stage.sv` parameter `EXEC_REDIR_INCYCLE` (default 0). Only decode's predicted redirect keeps the in-cycle launch added on 2026-08-31; the execute redirect (mispredict / trap / mret / interrupt) waits for `pc_q`, one cycle later. `bus_issue` is suppressed for that one cycle (`exec_redir_hold`) because `pc_q` still holds the wrong-path address until the edge, and `redir_launched_q` now arms only on an in-cycle launch. `=1` restores the 2026-08-31 form for an A/B.
   This is a **deliberate partial retreat** from item 1a's redirect-launch win, and the split is chosen so the retreat is cheap: the predicted redirect is 88-99% of control flow and keeps its cycle. Cost measured on the same images: quicksort 40135 → 41301 (+2.9%), CoreMark 402827 → 409827 cyc/iter (2.482 → 2.440 CM/MHz, +1.74%), Dhrystone 485 → 485 (unchanged — at 99.3% accuracy there are almost no execute redirects). Verified: all oracles `0x600D`, retire+writeback traces byte-identical, quicksort/ecall cosims PASS (29293 / 17), `uart_echo` ends `GOOD`.
   **The rule this run established, worth more than the fix:** an address that reaches a BSRAM's address pins pays a long physical tail (~9.8 ns here) on top of the logic that computes it, so only a *flop-or-PC-derived* address belongs on `issue_addr`. A register-file-derived one does not, however few mux levels it looks like in RTL.

1f. **Stores re-captured, D-mem load launch kept live — DONE 2026-09-01, closed and board-verified.** See the run-3 paragraph in Timing above for the trace and the reasoning. `EX_PERI_LAUNCH` became `EX_MEM_LAUNCH` and now carries peri accesses in either direction *plus* D-mem stores; only an aligned D-mem load drives the bus live from `alu_result`. `stall_o`, `wb_en_o`, `op_commits` and `csr_op_valid` are all flop-derived again.
   **The durable lesson from three runs on the same change:** what the LSU capture flop bought was never a shorter *address* path — it was keeping `alu_result` out of the pipeline's **control** network (stall / retire / commit). Each run named a different consumer (peri fabric, then the I-mem address leg, then `stall_o`), and only the third was the flop's real job. Before deleting a launch flop, ask which *control* signals become functions of the value it was holding, not how many mux levels the datapath gains.
   Verified: 7 oracles `0x600D`, 9 retire+writeback traces byte-identical, quicksort/ecall cosims PASS (29293 / 17), TBs 37/63/146 green, `uart_echo` ends `GOOD`.

2. **Cache controller over the in-package SDRAM** — GW2AR-18C carries 8 MiB (64 Mbit) SDRAM on a separate die, dedicated pins, unused. A write-back set-associative I/D-cache behind it would replace `u_imem`/`u_dmem` keeping the native interfaces (CPU unchanged). Point is **capacity, not speed** — BSRAM already answers in 1 cyc at 100% hit rate; a cache can at best match it. Buys programs >16 KiB. Use **Gowin soft-IP SDRAM controller**, don't write one; check its clock/burst config before fixing numbers below.
   Sizing: **Line = 32 B, not the 1 KiB full-page-burst figure** (which would cost ~260 core cyc/miss, hold a bank 5.12 µs against a 7.8 µs tREFI, and leave only ~16 lines total). At 32 B: 16 transfers + ~8 tRCD/CL/tRP ≈ 24 SDRAM cyc ≈ 12 core cyc/miss. **8 KiB per cache** = 16 KiB total, same BSRAM budget as today (16/46 blocks). 8 MiB=23 addr bits; 8 KiB/32 B=256 lines. **2-way**: 128 sets, offset5/index7/tag11+valid+dirty (~3.5 Kb tag array, negligible). Start 2-way — new path (`tag BSRAM→compare→hit→way mux→rdata`) is post-flop, doesn't touch the current limiter but competes with it at 50 MHz; go 4-way only if slack allows. Confirm SDRAM data width (16/32-bit) before fixing transfer counts.
   Later gotchas: **fetch's single `req_pc_q` assumes a fixed 1-cycle I-mem** — under variable latency `inflight_q` really reaches 2 and the older response is split at the younger read's PC stamp, silently wrong `fe_pc`. The `ifdef VERILATOR` assertion in `fetch_stage.sv` catches it; the fix is a depth-2 shadow FIFO for the in-flight PC, not a wider register. `fence.i` stops being a nop (needs D-cache flush + I-cache invalidate — a miss here looks like a decoder bug on silicon). MMIO must stay non-cacheable (`PERI_ADDR_BIT` decodes before the cache — keep it before). Need a dirty-line writeback buffer (avoid serial writeback-then-fill). Critical-word-first+early-restart (~5 cyc/miss). Clock domains: controller wants 100+ MHz vs core's 50 — either async FIFOs (breaks today's single-domain no-CDC) or run at 50 MHz and accept less bandwidth (do the simple thing first). Keep the 16 KiB BSRAM as a scratchpad/TCM for boot/ISRs rather than deleting it.
